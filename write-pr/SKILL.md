# Write PR

리뷰어가 대화 이력을 읽지 않고도 변경 이유, 달라지는 동작, 검증 근거와 판단할 지점을 알 수 있게 쓴다. 최종 diff를 설명하며 작업 일지를 쓰지 않는다.

기본 언어는 한국어다. 사용자의 언어 지정과 저장소의 작성 규칙·템플릿을 우선한다. 코드 식별자와 명령은 원문을 유지한다.

## 먼저 근거를 확보한다

- 요청이 새 PR 생성, 기존 PR 수정, 본문 초안 작성 중 무엇인지 구분한다. 관련 저장소 지침과 PR 템플릿이 있으면 확인한다.
- 사용자가 지정한 base/head를 우선한다. 기존 PR은 메타데이터에서, 새 PR은 저장소의 기본 브랜치와 작업 브랜치에서 확인한다. `main`이나 `master`를 임의로 고정하지 않는다.
- 실제 비교 범위의 diff와 커밋을 읽는다. 커밋 메시지·diff 통계·이전 PR 본문만으로 변경 내용을 추측하지 않는다. 미커밋 변경은 PR에 이미 포함된 변경과 구분한다.
- 현재 작업에서 확보한 실행 결과, 테스트 로그, CI 결과를 재사용한다. 문장을 채우려고 불필요한 검증을 반복하지 않는다. 결과가 없으면 미실행 또는 미확인으로 쓴다.
- 변경 목적처럼 설명을 크게 바꾸는 정보가 빠졌을 때만 질문한다. 파일명, 표현, 소제목 같은 일반적인 편집 선택은 스스로 해결한다.

## 제목과 첫 문단

제목은 핵심 변경이나 달라지는 동작을 구체적으로 말한다. 저장소가 Conventional Commits를 쓰면 기존 `type(scope): ...` 관례를 따른다. 포괄적인 "개선", "정리", "최적화"만으로 변경을 설명하지 않는다.

첫 문단에는 해결하려는 문제와 변경 후 결과를 연결한다. 필요하면 발생 조건과 전후 동작을 짧게 비교한다. 작성 과정, 도구 사용 내역, 대화에서 합의한 순서를 앞세우지 않는다.

범위나 설계가 바뀌었으면 제목과 본문 전체를 최종 구현 기준으로 다시 정리한다. 기존 설명 뒤에 수정 이력을 계속 붙이지 않는다. 버린 접근은 현재 선택의 중요한 제약이나 tradeoff를 설명할 때만 남긴다.

## 분량은 변경의 크기에 맞춘다

**작고 단순한 PR:** 짧은 문단과 검증 한 줄이면 충분하다. 소제목과 체크리스트를 채우기 위해 내용을 늘리지 않는다.

**구조 변경이나 운영 영향이 있는 PR:** 읽는 데 필요한 만큼 설명한다. 다음 내용을 의미별로 묶되, 모두 고정 소제목으로 만들 필요는 없다.

- 문제와 변경 후 동작
- 핵심 변경과 주요 경계·책임의 변화
- 실제 검증 결과와 남은 한계
- 리뷰어의 판단에 중요한 설계 선택이나 운영 영향

항목은 파일별 나열보다 동작·책임·결과별로 묶는다. 경로는 리뷰 위치를 찾는 데 도움 될 때만 적는다. 구조를 이해하는 데 실제로 도움이 되면 짧은 전후 예시, 디렉토리 트리, 다이어그램을 사용한다.

## 검증을 정확하게 표현한다

- 명령, 검증한 동작, 결과를 필요한 수준으로 연결한다. 테스트 수만으로 충분히 검증됐다고 결론내리지 않는다.
- 단위 테스트의 mock, 실제 서비스 통합, 빌드된 배포 산출물 실행, 실제 운영 배포를 구분한다. 성공한 단계로 다른 단계까지 성공했다고 확대하지 않는다.
- 실패를 수정한 경우 최종 구현에 적용되는 결과를 쓴다. 테스트가 이전 head에서 수행됐거나 환경 차이가 남으면 그 한계를 밝힌다. PR의 CI 상태를 언급할 때는 현재 head의 결과인지 확인한다.
- 임시 서비스나 fixture를 사용했다면 검증한 경계를 설명한다. 실패 주입으로 확인한 경로를 실제 장애 재현으로 표현하지 않는다.
- 긴 로그나 모든 테스트 이름을 복사하지 않는다. 리뷰어가 결론을 판단하는 데 필요한 결과와 중요한 제한을 남긴다.
- 미수행 항목을 통과로, 계획을 완료로 쓰지 않는다. 저장소 문서에 적힌 설명도 실행 증거로 취급하지 않는다.

## 리뷰·운영 영향은 실제로 중요한 것만

호환성, 데이터·스키마 변경, 설정 및 배포 전환, 의존성 patch, 장애 시 동작, 롤백 제약처럼 이번 변경을 판단하는 데 필요한 사항을 포함한다. 관련 없는 위험 목록이나 상투적인 경고는 추가하지 않는다.

외부 동작이 달라지는 변경은 구체적인 전후 예시로 설명한다. 내부 리팩터링은 유지되는 계약을 리뷰에 필요할 때 명시한다. 별도 작업이 꼭 필요한 경우 현재 완료된 범위와 남은 일을 분리한다.

관련 이슈는 확인한 것만 연결한다. 이슈를 완전히 해결하는 것이 확인된 경우에만 자동 종료 키워드를 사용한다. 리뷰어·팀·이슈를 추측해서 태그하지 않는다.

## 초안과 게시의 범위를 지킨다

본문 초안이나 스킬 작성만 요청받았으면 요청한 결과물을 제공한다. 그 요청만으로 실제 PR을 생성·수정하지 않는다.

사용자가 PR 생성 또는 수정을 이미 요청했다면 해당 게시 작업은 승인된 범위다. 작성 완료 뒤 같은 허락을 다시 요구하지 않는다. 사용자가 지정한 draft/ready 상태, base, 리뷰어 설정을 보존한다. PR 작성 요청을 merge, 배포, 리뷰 요청이나 별도 메시지 전송의 허가로 확대하지 않는다.

게시할 때는 구조화된 API 인자를 사용하거나, 실제 개행을 보존한 임시 파일을 `gh ... --body-file`로 전달한다. 성공 후 URL·제목·base/head와 대상 커밋을 확인하고, 연결 기능이 있으면 PR을 현재 작업에 첨부한다.

사용자에게는 PR 링크와 핵심 결과를 짧게 전달한다. 게시하지 않았다면 제목과 본문 초안을 바로 제시한다.

## 마지막 편집

아래 질문으로 최종 원고를 점검하고 직접 고친다. 이를 별도의 사용자 승인 단계나 빈 체크리스트로 만들지 않는다.

- 첫 문단만 읽어도 문제와 결과를 이해할 수 있는가?
- 제목과 주요 주장이 최종 diff 및 근거와 맞는가?
- 반복된 내용, 대화 이력, 도구 자랑, 필요 없는 구현 세부가 남았는가?
- 검증 결과와 미확인 범위를 과장 없이 구분했는가?
- 리뷰어가 실제로 판단해야 할 중요한 영향이 설명됐는가?

스킬의 권고보다 사용자의 명시적 요구와 저장소 규칙을 우선한다.
